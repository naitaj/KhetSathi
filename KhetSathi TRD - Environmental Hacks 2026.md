# KhetSathi: Technical Requirements Document (TRD)

Environmental Hacks 2026 | Track 2: Heat and Water | Build window: 8–11 Oct 2026

## 0. Conventions and implementation assumptions

- **MUST** = required for the Environmental Hacks MVP. **SHOULD** = ship if time permits. **NICE** = optional stretch. **FUTURE** = not part of the hackathon MVP. **DEMO** = demo-only configuration. **SIM** = generated by simulation, not field-measured.
- Agronomic parameters such as crop coefficients (`Kc`), allowed depletion fraction (`p`), rainfall effectiveness, maximum irrigation depth and duration caps are configurable. Values are placeholders until checked against cited agronomic sources such as FAO-56 and, where appropriate, local extension guidance. The TRD does not treat placeholder values as authoritative agronomic advice.
- No field trial, farmer interview, measured groundwater change or measured water saving is claimed. Personas are design personas. Simulation results are explicitly labelled **SIMULATED**.
- Units: area in hectares or m² as noted, water depth in mm, water volume in litres (L), flow in L/min, duration in minutes, energy in kWh. `1 mm` over `1 m²` equals `1 L`.
- Timestamps are stored as UTC ISO-8601 and displayed in Asia/Kolkata (IST). Decision dates are IST calendar dates.
- **Primary weather provider:** Open-Meteo for the MVP, subject to verifying required fields and usage terms before deployment. NASA POWER is not a second runtime dependency for the MVP; it may be considered later.
- **AWS region:** `ap-south-1` (Mumbai) is the default. On Day 1, verify the required AWS services and Hindi (`hi-IN`) Polly voice availability. If Polly voice is unavailable in-region, the voice Lambda may call Polly in a supported region while the rest of the stack remains in Mumbai, or voice may be disabled with text fallback.
- IDs use prefixed ULIDs, for example `plt_`, `frm_`, `dec_`, `fbk_`, `sim_`.

## 1. System overview

### 1.1 Technical objective

KhetSathi is a small event-driven, serverless system that produces one irrigation decision per field per day. The decision is based on crop state, weather/rainfall and a simple root-zone water balance, then passed through an independent agronomic safety layer.

The core technical invariant is:

> **AI or optimization may propose an action; only the deterministic safety layer can approve the deployable action.**

The MVP must work without the optional ML/RL layer, satellite input, sensors or voice.

### 1.2 Architecture style

The architecture has two execution paths sharing the same pure decision engine:

```text
Scheduled path:
EventBridge Scheduler → daily_decision_handler → Decision Engine → Safety Layer → DynamoDB
                                                     ↓
                                                   Polly → S3

Request path:
PWA → API Gateway → Lambda → DynamoDB/S3 → JSON/audio URL → PWA
```

No VPC, EC2, ECS, EKS, MQTT broker, relational database or always-on application server is used in the MVP.

### 1.4 Runtime principles

1. Decision correctness is defined as software reproducibility and safety validation, not as a claim of agronomic perfection.
2. The final decision is deterministic after safety validation for the same stored inputs, configuration and model artifact.
3. Every decision stores provenance, rules triggered, safety result and version information.
4. A daily decision is idempotent per `(plot_id, decision_date)`.
5. No error path emits an unconstrained irrigation recommendation.
6. Optional services cannot block the core decision.

## 6. Decision pipeline

```text
Environmental Inputs
      ↓
Plot State
      ↓
Baseline Counterfactual
      ↓
Deterministic Water-Balance Proposal
      ↓
Optional Model Proposal
      ↓
Safety Layer
      ↓
Final Decision
      ↓
M2 Rule Explanation
      ↓
PWA / Hindi Voice
      ↓
Farmer Feedback
```

### 6.1 Core decision rule

The MVP decision engine is deterministic. It estimates crop water requirement and recommends a safe irrigation amount based on the available data and configured agronomic constraints.

It does **not** claim to find the globally optimal irrigation amount or prove field-level groundwater savings.

### 6.2 Optional RL

RL is a stretch component only. If it is not implemented or does not improve simulation results under the same constraints, it is removed without changing the product story.

If retained:

- State: depletion ratio, crop stage, projected ETc, forecast rain and days since last irrigation.
- Action: skip or a small set of duration levels.
- Reward: penalize unnecessary water use and pump-hours while strongly penalizing depletion beyond the allowed limit.
- Training: local simulation only; no GPU or AWS training service.
- Inference: small artifact packaged with the Lambda deployment.
- Safety: every output passes the same safety layer.
- Acceptance gate: it may be enabled only if held-out simulation shows no increase in stress days and a meaningful reduction in water use; otherwise it remains disabled.

## 7. Agronomic state and water balance

The MVP uses a simplified single root-zone bucket inspired by FAO-56 concepts.

```text
ETc = Kc × ET0
TAW = 1000 × (FC − WP) × root_depth_m
RAW = p × TAW
Dr_new = clamp(Dr_old + ETc − effective_rain − net_irrigation, 0, TAW)
```

All coefficients and thresholds are configurable and source-reviewed before being presented as agronomically grounded.

### 7.1 Required state

- Crop
- Crop stage
- Kc
- Root depth
- TAW
- RAW
- Current depletion `Dr`
- Previous rain
- Forecast rain
- Previous irrigation
- Pump flow
- Application efficiency
- Data freshness
- Confidence/degraded flag

### 7.2 Irrigation duration

For a proposed net irrigation depth:

```text
Gross volume (L) = net_depth_mm × area_m2 / application_efficiency
Duration (min) = gross_volume_L / pump_flow_L_per_min
```

Duration is rounded to the configured increment and bounded by the safety cap.

## 8. Safety layer

The safety layer is independent of any model and has no model imports.

### 8.1 Safety checks

| ID | Check | Outcome |
|---|---|---|
| S01 | Critical input plausibility | Veto/fallback if impossible values are detected |
| S02 | Data freshness | Lower confidence or conservative fallback |
| S03 | Depletion floor | Veto unnecessary irrigation |
| S04 | Rain-skip | Skip only when configured effective rainfall covers the required need |
| S05 | Minimum interval | Prevent repeated irrigation within configured interval |
| S06 | Maximum duration | Cap or veto |
| S07 | Maximum daily irrigation | Cap or veto |
| S08 | Crop-stage restriction | Cap/modify according to configuration |
| S09 | Field-capacity protection | Do not recommend more net water than depletion requires |
| S10 | Severe-depletion protection | May upgrade an unsafe SKIP to a capped irrigation action |
| S11 | Low confidence | Prevent aggressive recommendations when evidence is weak |
| S12 | Window sanity | Move or reject actions outside configured irrigation windows |

### 8.2 Safety outcomes

`APPROVED`, `MODIFIED`, `VETOED`, or `FAIL_CLOSED`.

If a learned proposal is vetoed, the deterministic water-balance proposal is re-evaluated. If the safety engine itself fails, no unvalidated irrigation instruction is emitted.

## 13. Authentication and API access

The hackathon MVP does not use Cognito or another production identity platform.

### 13.1 Demo access mechanism

Each plot receives a randomly generated, high-entropy `plot_access_token` at onboarding. The frontend stores it locally and sends:

```http
Authorization: Bearer <plot_access_token>
```

The backend stores only a one-way hash of the token. A plot ID alone is not sufficient to access the plot.

The access token is returned once after plot creation. A token cannot list other plots.

This is explicitly **demo-scale access control, not production authentication**.

### 13.2 Public API rules

- No `/admin/run` public endpoint in production.
- No endpoint lists all plots unless the future FPO role is authenticated.
- API Gateway throttling is enabled.
- Request bodies are schema-validated before the decision engine runs.
- Production CORS allows only the Amplify origin; localhost is allowed only in development.

## 18. Error handling and fallback strategy

### 18.1 General fallback ladder

```text
LIVE DATA
   ↓ fails
RECENT CACHED DATA
   ↓ unavailable/stale
HISTORICAL/REPLAY DATA where safe
   ↓ unavailable
DETERMINISTIC CONSERVATIVE MODE
   ↓ cannot validate safely
FAIL CLOSED: no automatic irrigation instruction
```

### 18.2 Error matrix

| Failure | System behavior |
|---|---|
| Open-Meteo timeout | Retry, then cached snapshot, then conservative mode |
| Weather stale | Visible LOW confidence; no skip based solely on stale forecast |
| Satellite unavailable | Ignore satellite; decision continues |
| Sensor unavailable | Ignore sensor; modeled depletion continues |
| Model unavailable | Deterministic water-balance proposal |
| Safety engine exception | No unvalidated irrigation instruction |
| Polly failure | Text/icons remain available |
| S3 audio failure | Decision remains valid; audio marked unavailable |
| DynamoDB write failure | Do not serve the write as final; return dependency error/log failure |
| EventBridge failure | Scheduler retries; CloudWatch alarm; lazy decision on first GET may recover if safe |
| API failure | PWA can display cached last decision with timestamp |
| Poor connectivity | App shell and cached decision remain available; feedback waits until online |

## 20. Non-functional requirements

### Performance

- **Daily demo target:** 10–20 seeded plots processed successfully within 60 seconds.
- **Today's Decision API target:** p95 under 1 second on a warm Lambda when the decision already exists in DynamoDB.
- Decision computation itself should remain deterministic and lightweight enough to fit within the Lambda timeout.

### Reliability

- Daily decision write is idempotent.
- Optional components cannot prevent a safe deterministic decision.
- No duplicate decision for the same `(plot_id, decision_date)`.

### Safety

- No final irrigation decision bypasses the safety layer.
- Model failure cannot remove safety constraints.
- Safety failure produces fail-closed behavior.

### Cost

- Use on-demand DynamoDB.
- Avoid always-on compute.
- Keep simulation scenarios small enough for Lambda.
- Do not run optional demo resources continuously.
- Verify actual AWS cost before submission rather than claiming a guaranteed amount.

### Reproducibility

- Infrastructure deployable from source using SAM.
- Simulation reproducible from fixed scenario, seed and configuration.
- Decision reproducible from stored inputs/config/model versions.

## 28. Rollback and recovery

The hackathon does not need enterprise disaster recovery, but the team must have a simple recovery procedure.

### 28.1 Backend rollback

- Keep the last known-good SAM deployment configuration.
- Do not perform destructive schema migrations during the hackathon.
- If a Lambda deployment breaks the demo, redeploy the last known-good commit/configuration using SAM.

### 28.2 Frontend rollback

Amplify deployment must remain tied to Git commits. If the latest frontend build fails, redeploy the last known-good commit.

### 28.3 Data recovery

- Keep demo seed data and scenario files in the repository.
- Simulation inputs are reproducible from source.
- Critical demo DynamoDB records should be recreatable from the onboarding script rather than treated as irreplaceable state.

### 28.4 Recovery test

Before final submission, intentionally reproduce one failed deployment or handler error in a safe test environment and confirm that the team can restore the previous working version.

## 33. Architecture decision records

### ADR-01 — Serverless AWS architecture

Chosen to minimize infrastructure management and make a working four-day build possible.

### ADR-02 — DynamoDB instead of PostgreSQL/TimescaleDB

Chosen to reduce operational setup and keep the MVP focused on simple access patterns.

### ADR-03 — EventBridge Scheduler

Chosen to model the product's daily automated decision loop without an always-on service.

### ADR-04 — Safety layer outside the learned model

Chosen so model behavior can never bypass agronomic constraints.

### ADR-05 — Deterministic baseline

Chosen so impact comparisons have a transparent counterfactual.

### ADR-06 — Optional RL

Chosen only as stretch functionality because no labelled field dataset exists and the hackathon does not require ML for a credible MVP.

### ADR-07 — Satellite as optional enrichment

Chosen to prevent geospatial data availability from becoming a critical dependency.

### ADR-08 — No public admin route

Chosen to reduce unauthorized control risk and keep operational actions in AWS tooling during the hackathon.

### ADR-09 — No offline feedback sync in core MVP

Chosen to avoid promising a feature that is not necessary to demonstrate the environmental solution.
